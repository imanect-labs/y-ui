# 評価計画（事前登録）

MiniUI の記法を Shiki の図の出し方の標準にするかを、実測で決めるための計画。
**採点基準と採用基準は、実モデルで評価を実行する前にこの文書で固定する。** 結果を見てから基準を変える場合は、変更点と理由をこの文書に追記し、変更前の基準での判定も併記する。

## 1. 問い

1. 小さめのオンプレモデル（Gemma 4 31B FP8）で、本文中に書く MiniUI は、今の `emit_ui`（ツール呼び出し＋入れ子の JSON）より正しく図を出せるか。
2. SaaS の低コストモデル（GPT-6 Luna）で、MiniUI にしても悪くならないか。
3. 差が出るなら、それは「ツールか本文か」によるのか、「JSON か独自記法か」によるのか。
4. 説明文の長さ（簡易版 / 完全版）でどれだけ変わるか。

## 2. モデル

| 名前 | 用途 | 接続 | 環境変数 |
|---|---|---|---|
| `gemma` | オンプレ（vLLM、OpenAI 互換） | `GEMMA_BASE_URL`（例: `http://host:8000/v1`） | `GEMMA_BASE_URL`、`GEMMA_API_KEY`（任意）、`GEMMA_MODEL`（既定 `google/gemma-4-31B-it`） |
| `luna` | SaaS | OpenAI API | `OPENAI_API_KEY`、`OPENAI_BASE_URL`（任意）、`LUNA_MODEL`（既定 `gpt-6-luna`） |

思考の深さ（effort）ごとの追加パラメータは `eval/models.json`。**実機での確認が必要:** Luna に Chat Completions の `reasoning_effort` が効くか、Gemma 4 の思考の切り替えが vLLM で `chat_template_kwargs.enable_thinking` で効くか。Gemma の vLLM は `--enable-auto-tool-choice --tool-call-parser gemma4` を付けて起動する（方式 A に必要）。

## 3. 方式

| ID | 方式 | 説明文 | 対象の課題 |
|---|---|---|---|
| A | 今の `emit_ui`（ツール＋JSON）。説明文は Shiki のソースから毎回読む。検証に失敗したら最大 2 回まで直させる（Shiki と同じ） | ツール定義 約 3,300 字 | 全課題 |
| A2 | A の 1 回目をツール指定（`tool_choice`）で強制。vLLM では出力の形が強制される | 同上 | 図を出すべき課題のみ |
| B | MiniUI を本文中に書く。簡易版の説明 | 約 400 字 | 全課題 |
| C | MiniUI を本文中に書く。完全版の説明 | 約 950 字 | 全課題 |
| D | 短い JSON を本文中の ` ```uijson ` に書く | 約 1,050 字 | 全課題 |
| E | Mermaid の flowchart | 約 450 字 | flow / stack のみ |

文字数は `pnpm eval prompts` の出力（system メッセージ＋ツール定義）。共通の system は `eval/prompts/base.md`。利用者メッセージは「# 参考資料」（課題の資料を `[1]` として）と「# 質問」。

## 4. 課題（141 件、`eval/tasks/tasks.jsonl`）

| 種類 | 件数 | 内容 |
|---|---:|---|
| bar | 25 | 資料の数値（文章・表・箇条書き・レポートの 4 形式）を棒グラフに |
| line | 20 | 時系列を折れ線に |
| stat | 20 | 文章中の指標を数値カードに |
| long | 10 | 24〜47 行の書き写し（都道府県別・日別・時間帯別） |
| jpnum | 10 | `1億2,000万円`・`△3,500万円`・全角数字 |
| flow | 20 | 業務手順の説明文から流れ図（分岐あり 14 件） |
| stack | 16 | 構成の説明文から構成図 |
| none-unneeded | 10 | 図が不要な質問（規程の確認・文面作成など）。図を出さないのが正解 |
| none-nodata | 10 | 図を求められるが資料に数値が無い。数値のある図を出さないのが正解 |

グラフと数値カードの課題は `eval/src/tasks/generate.ts` が固定シードで生成する。flow / stack は `eval/src/tasks/handwritten.ts` に手で書き、正解は MiniUI のソースで書いて解析する。`tasks.jsonl` を変えたら `pnpm eval build-tasks` で作り直し、テスト（生成器の出力と一致すること）を通す。

## 5. 採点（`eval/src/score.ts`）

出力から図を取り出し（方式ごとの抽出器）、正解の中間表現と比べる。図が複数あれば最も良いものを採る。

- **bar / line:** ラベルを表記ゆれ込みで対応付け、系列の対応と倍率（`万円` と `円` のような 10 のべき乗）は一致セルが最大になるように選ぶ。値は相対誤差 0.5% 以内で一致とする。
  **合格 =** 種類が正しい（質問が種類を指定していればその種類、指定が無い時系列は bar / line どちらも可）かつ 全セル一致 かつ 余分な行なし かつ 資料に無い数値なし。
- **stat:** 項目名で対応付け、値は数値として（倍率込みで）または文字列として比べる。
  **合格 =** 全項目一致 かつ 資料に無い数値なし（資料に無い追加の項目は、数値でなければ許す）。
- **flow:** ノードを表記ゆれ込みで 1 対 1 に対応付け、有向辺の F1 を取る。分岐（出る辺が 2 本以上のノード）の辺だけ、ラベルの一致も見る。
  **合格 =** 辺の F1 ≥ 0.85 かつ 分岐ラベルの一致率 ≥ 0.75。
- **stack:** 層の箱を対応付けた F1、対応した箱どうしの層の中の要素の F1、層の上下関係（同じ段かどうかを含む）の一致率を取る。
  **合格 =** 箱の F1 ≥ 0.85 かつ 要素の F1 ≥ 0.85 かつ 上下関係の一致率 ≥ 0.95。
- **none-unneeded:** 図を 1 つも出さなければ合格。
- **none-nodata:** 数値を含む図（グラフ・数値カード）を出さなければ合格。
- **表記ゆれ:** NFKC・小文字化・空白と記号の除去のあと、完全一致 1.0、包含 0.9、ひらがなを除いた骨格の一致 0.85、それ以外は文字 bigram の Dice 係数。0.5 以上を対応付けの候補とする。

あわせて記録する指標: 構文の成功率（図を出そうとした出力のうち、全部が構文として正しかった割合）、初回の構文成功率（A の修正ループの前）、数値の捏造率、入出力トークン、最初の図が描けるまでの時間（B / C は生成途中で 1 行以上描けた時刻、D / E はフェンスが閉じた時刻、A は検証を通ったツール呼び出しが終わった時刻）、全体の時間。

## 6. 採用基準（`eval/src/report.ts` の `CRITERIA`）

主条件: effort = `low`、文脈の水増しなし。A と B の比較は、A が表現できる種類（bar・line・stat・long・jpnum・none-unneeded・none-nodata）に限る。

次の両方を満たせば、MiniUI（B）を Shiki の図の出し方の標準として採用する。

1. **Gemma:** B の合格率が A より **10 ポイント以上高い**、または、差が **-3 ポイント以内**で入出力トークンの合計が A の **0.5 倍以下**。
2. **Luna:** B の合格率が A より **3 ポイントを超えて低くない**。

flow / stack は A では表現できないため、B・C・D・E の比較として別に報告する（採用判定には使わない）。

## 7. 実行条件

| 条件 | 値 |
|---|---|
| 繰り返し | 各課題 × 方式 × モデル × effort で 3 回 |
| effort | 主条件 `low`。副条件 `high` |
| 文脈の水増し | 主条件なし。副条件として 12,000 字（`--pad-chars 12000 --pad-dir <資料のディレクトリ>`）。数字を多く含む段落は使わない |
| temperature | 指定しない（各モデルの既定値） |
| 最大出力 | 8,192 トークン |

主条件の生成数: 方式 A・B・C・D は 141 件、A2 は 121 件、E は 36 件 → 1 モデル 1 effort あたり 3 回で約 2,400 生成。

## 8. 手順

```bash
pnpm install
pnpm test                         # パーサ・採点・抽出・配線（模範解答モデル）のテスト
pnpm eval truncation              # 生成途中で切れたときの検証（モデル不要）
pnpm eval run --mock --seeds 1    # 配線の確認（API を呼ばない）

# 本番（Shiki のソースを方式 A の説明文として読むため、隣に shiki-platform を置くか --shiki-root で指定）
pnpm eval run --models gemma --efforts low --seeds 3 --run-id gemma-low
pnpm eval run --models luna  --efforts low --seeds 3 --run-id luna-low
pnpm eval report eval/results/<run-id>
```

結果は `eval/results/<run-id>/results.jsonl`（1 生成 1 行。出力の全文を含む）と `report.md`。中断しても同じ `--run-id` で再開できる。採点を直したら `pnpm eval rescore <dir>` で採点し直す。

## 9. 既知の制約

- **A の検証は近似。** Shiki の `validate_spec` の主な規則（未知のキー、`x` は文字列、`y` は数値、種類の閉集合など）を TS で再現している。正確に合わせるには、`SHIKI_VALIDATE_CMD` に本物の検証コマンドを指定する（標準入力に spec の JSON、標準出力に `{"ok":bool,"errors":[...]}`）。Shiki 側にこのコマンドは未実装。
- **A の flow は stepper / timeline からの写し。** 分岐は表現できない。stack は写さない（Shiki のカタログに無い）。
- **E の stack は横並びを表現できない。** Mermaid の flowchart には「同じ段に並べる」書き方が無いため、横並びの課題では上下関係の一致率が下がる。模範解答でも stack の合格率は 44%。E の stack の数字は、この制約込みで読む。
- **「図が役に立ったか」は自動採点しない。** 主条件の結果から、各方式 20 件ずつを抜き出して人が確認する。
