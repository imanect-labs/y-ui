# app（入力してボタンで実行する画面）設計草案

状態: Yui 側（記法・IR・描画・`onAction`）は実装済み。Shiki 側（§6）は方針が決まり、実装中。

## 1. 目的

モデルが、入力部品（文字・数値・選択・日付など）とボタンを並べた小さな画面を書き、利用者が値を入れてボタンを押すと、ホスト（Shiki）がその値でワークフローを起動する（または会話に送る）。1 つの画面に複数の「機能」（入力のまとまりとボタン）を並べられる。

- 例: 経費の申請と月次の集計を 1 つの画面に。休暇の申請。問い合わせの振り分け。データの再取り込み。
- calc（画面内で完結する計算、段階 2）の次の段階 3（ホストのアクション）にあたる。

## 2. 原則

1. **Yui は実行しない。** Yui はボタンが押されたことと入力値をホストに渡す（`onAction`）だけ。サーバーを呼ぶ・URL を開く・スクリプトを実行する経路を持たない。
2. **モデルが書けるのは実行先の名前だけ。** `-> workflow 経費申請` の「経費申請」をワークフローに解決し、版を固定するのはホスト。解決は **書いた側（会話の主体）** の権限で行い、実行は **押した人** の権限で行う（Shiki の `emit_ui` と同じ）。
3. **値の検証は 2 回。** 画面では記法の定義（必須・範囲・選択肢）で検証し、ホストはサーバーで同じ定義とワークフローの入力スキーマで検証し直す（画面の検証は便宜で、信用しない）。
4. **束縛の無い場所では押せない。** ホストが束縛を検証・保存していない場所（貼り付けたブロック・ノート・ストリーミング中など）では、ボタンは無効にして「この場所では実行できません」を出す。
5. **データだけを書かせる。** 見た目（配置・色・幅）は Yui が決める。

## 3. 記法

````
```ui
app 経費の処理
## 経費の申請
> 領収書の内容を入力してください。
件名 = text 必須 例 4月 大阪出張の交通費
金額 = number 1..1000000 円 必須 as amount
区分 = choice 交通費 | 出張費 | 備品
日付 = date 必須
内容 = textarea
立替 = toggle
button 申請する -> workflow 経費申請

## 月次の集計
対象月 = month 必須
部署 = choice 営業 | 開発 | 管理 multi
button 集計する -> workflow 月次集計
button 会話で相談する -> chat
```
````

- `## 見出し`: 機能（入力のまとまりとボタン）。無ければ全体で 1 つの機能。`> 説明` はその機能の説明。
- `ラベル = 種類 [オプション]`: 入力部品。ラベルは画面にそのまま出る。

| 種類 | 意味 | オプション |
|---|---|---|
| `text` | 1 行の文字 | `例 …`（入力の例）・`初期 …` |
| `textarea` | 複数行の文字 | `例 …` |
| `number` | 数値 | `最小..最大`（両方を書く。`1..` のような片側だけの範囲は読まずに警告）・`step 刻み`・`初期 値`・単位 |
| `slider` / `count` | calc と同じ | calc と同じ |
| `choice a \| b \| c` | 選択（`表示名=値` も可。選択肢の中の縦棒は前にバックスラッシュを付ける（表の下）） | `multi`（複数選択） |
| `date` / `month` | 日付・年月 | `初期 2025-04-01` |
| `toggle` | オン・オフ | `初期 オン` |

  choice の選択肢に縦棒（`|`・`｜`）を含めるときは `区分 = choice A\|B | C` のように前にバックスラッシュを付ける（選択肢は「A|B」と「C」。choice の初期値も同じ）。

  共通: `必須`（`required`）、`as キー`（実行先に渡す名前。無ければラベル。ワークフローの入力名が英字ならこれで合わせる）。

- `button ラベル -> workflow 名前`: その機能の入力値で、名前のワークフローを起動する。`-> chat`: 入力値を会話に送る（モデルが続きを答える）。`confirm` を付けると押した後に確認を挟む（workflow は既定で確認する）。
- 1 つの機能のボタンは、その機能の入力値だけを送る。
- `note:` は画面の下の注記。
- 上限: 機能 6、1 機能の入力 20、全体の入力 40、ボタン 1 機能 3。ラベル 40 文字。

`file`（ファイルの添付）は v1 では入れない（ストレージのノードの参照と権限の設計が要るため）。

## 4. IR と API（`@imanect/yui`）

```ts
interface AppField { key: string; label: string; type: "text" | "textarea" | "number" | "slider" | "count" | "choice" | "date" | "month" | "toggle"; required: boolean; placeholder?: string; initial?: string | number | boolean | string[]; min?: number; max?: number; step?: number; unit?: string; options?: { label: string; value: string }[]; multi?: boolean }
interface AppAction { id: string; label: string; target: { kind: "workflow"; name: string } | { kind: "chat" }; confirm: boolean }
interface AppSection { title?: string; desc?: string; fields: AppField[]; actions: AppAction[] }
interface AppFigure extends FigureBase { kind: "app"; sections: AppSection[] }
```

- `id` はソースの順の `a1`・`a2`…（同じソースなら同じ id。ホストはこれを束縛の id にする）。
- `validateAppValues(figure, actionId, values)`: 必須・型・範囲・選択肢の検証（純粋関数。ホストのサーバーが同じ規則を実装する手本）。
- React: `<YuiFigure figure onAction />`。`onAction({ actionId, action, values }) => Promise<{ ok: boolean; message?: string } | void>`。`onAction` が無ければボタンは無効。押してから結果が返るまでボタンを無効にし（二重押しを防ぐ）、結果の文言を機能の下に出す。
- 静止画（SVG・書き出し）は、入力欄とボタンの見た目だけ（値は空か初期値）。テキスト化は入力の一覧と「ボタン: 申請する（経費申請を起動）」。

## 5. 安全性（Yui 側）

- 入力値はホストに渡すだけで、Yui は保存・送信しない。
- 実行先の名前・ラベルは文字列として描く（リンク・HTML にしない）。
- 確認（`confirm`）の画面には、実行先の名前と送る値の一覧を出す（何が起きるかを押す人が分かるように）。
- 貼り付けで取り込んだブロック・表示専用の場所では、ホストが `onAction` を渡さない（docs/export.md の段階 3 の扱い）。

## 6. Shiki への組み込み（提案・human の確認待ち）

調査（2026-10-15、shiki-platform main 26b3d41）で分かったこと:

- `emit_ui`（`crates/gui`）は、フォームの送信をワークフローに束縛できる（`ActionBinding::Workflow`）。束縛はサーバーで検証され、名前は話者の閲覧権限で解決して版を固定し、`POST /threads/{t}/messages/{m}/ui-actions` で実行される。クライアントは束縛を送れない。
- ```ui ブロックは `docs/design.md` §4.7 で表示専用（操作・束縛を持たない）。

決定（2026-10-15、human）: **本文の ```ui ブロックの app を直接操作できるようにする**（`docs/design.md` §4.7 の「表示専用」を、app に限って改める）。押せる人は「会話の編集者 ∧ ワークフローの実行権限」。起動の結果は会話に残す。

経路の案:

1. 回答が確定したとき、サーバー（チャットのワーカー）が本文の ```ui app ブロックを読み（Rust 版の app のパーサ。TS 版と同じ規則・同じ課題集で確かめる）、`-> workflow 名前` を **回答した主体の権限** で解決して版を固定する（`SpecValidator::resolve_workflow` と同じ）。解決できない名前のボタンは束縛を作らない（画面では無効）。
2. 束縛（ボタンの id → `ActionBinding`）と部品の定義を、そのメッセージに表示しない宣言として保存する。ブロックはソースの SHA-256 で識別し、ボタンの id は `{ブロックのハッシュ}:{a1}`。
3. 画面は宣言のあるブロックだけボタンを有効にし、`onAction` を既存の `POST /threads/{t}/messages/{m}/ui-actions` につなぐ（`action_id` と値と冪等キー）。
4. サーバーは宣言から束縛を引き、押した人が会話の編集者かを確かめ、値を部品の定義（`validateAppValues` と同じ規則）で検証し、冪等キーで二重起動を防いでから、既存の `ActionDispatcher` で起動する（押した人の権限で）。
5. 起動・完了・失敗を会話に記録する（モデルが次の回答で参照できる）。

あわせて閉じたい穴（今の `emit_ui` の workflow 束縛にもある）:

- 数値の入力部品が `FormField` に無い（`number` を足す）。
- ワークフローの起動で、会話の **編集者** の確認が無い（閲覧者でも押せる）。`chat.submit` と同じく編集者を要求する。
- 値をワークフローの `input_schema` で検証していない。部品の定義とスキーマの両方で検証する。
- 二重起動の防止（workflow 束縛は使い捨てでない）。押すたびに冪等キーを付け、同じキーは 1 回だけ起動する。
- 確認の画面（ワークフローは副作用があるので、既定で確認を挟む）。
- 起動の結果（run の状態）を会話に残す（今はブラウザに run_id を返すだけで、モデルも知らない）。
